# 0006. Прикладной слой партии: стол, источник ходов соперника, Bloc

## Контекст

Движок (ADR 0001) даёт `start`, `apply`, `project` и `eventsFor`, бот (ADR 0004) — `MatchBot.decide(state, seat)`,
сеть (ADR 0005) — хост и клиент партии. Экраны поля ждут макетов, но партию уже нужно вести от выбранных колод до итога
в двух режимах: hot-seat (два человека на одном телефоне) и против бота. Сетевой режим подключится позже и не должен
менять держатель состояния экрана.

Разница между режимами в том, где живёт полное состояние партии:

- hot-seat и бот: на этом устройстве, ходы проверяет местный движок;
- сеть: на хосте (`MatchHost`); у гостя есть только проекции из `MatchClient`, у хоста его собственный игрок
  подключается к `MatchHost` через `InMemoryTransport` как обычный клиент.

## Решение

### Стол партии `MatchTable` (domain фичи `match`)

Экран видит партию только через интерфейс стола:

- `localSeats` — места, за которые ходят люди на этом устройстве: оба в hot-seat, одно против бота и по сети;
- `updates` — поток для единственного подписчика (держателя состояния): `ViewsChanged` (проекции всех здешних мест
  сразу и события для каждого), `IntentRefused` (движок отклонил действие), `TableFailed` (соперник не смог ходить);
- `submit(seat, intent)` — действие за здешнее место; итог приходит в `updates`;
- `close()`.

Проекции всех здешних мест приходят одним обновлением: иначе экран hot-seat видел бы одно место уже после хода, а другое
ещё до него.

Это и есть абстракция источника ходов соперника, общая для всех режимов: держатель состояния не знает, кто сидит
напротив. Реализации:

- `LocalMatchTable` (есть): полное состояние здесь, каждый ход проверяет движок. Места без человека занимают агенты. Стол — `PausableTable`: пока игрок открыл паузу матча (любой слой `PauseLayer`), экран шлёт `MatchPauseChanged`, `MatchBloc` вызывает `setPaused`, и бот не думает и не ходит. Общий для стола и `BotAgent` объект `MatchPause` отсчитывает «размышление» бота без времени паузы и держит готовое решение до её конца. Сетевой стол паузу не замечает: соперник-человек ходит сам.
- Сетевой стол (будет с Wi-Fi): поверх `MatchClient`, `ViewChanged` → `ViewsChanged` для своего места,
  `ActionRefused` → `IntentRefused` (номер запроса сопоставляется с отправленным намерением), потеря связи и пауза —
  отдельные обновления, которые добавятся вместе с экраном. На хосте рядом работает `MatchHost`.

### Агент места `SeatAgent` для местной партии

`SeatAgent.decide(state, seat) → Future<Intent?>`: ход за место без человека. Стол спрашивает агентов после каждого
изменения партии, пока им есть что делать. Решение асинхронное, поэтому бот может «думать» с паузой, а позже считать
ход в изоляте. Если, пока агент думал, партия изменилась (при пересдаче человек и бот действуют одновременно), решение
отбрасывается и агент решает заново. Отказ движка на ход агента, исключение агента или его молчание, когда партия ждёт
именно его, — `TableFailed`: это ошибка бота или движка, а не позиция партии.

`BotAgent` оборачивает `MatchBot` (по умолчанию `GreedyBot`) и делает паузу `thinkTime` перед ходом (700 мс в
приложении, ноль в тестах).

Сетевой игрок не агент местного стола: авторитетная сторона сети — `MatchHost` со своим журналом, паузой
и переподключением, и повторять его в столе незачем.

### Сценарии (application)

- `StartMatch(LocalMatchRequest)`: контент из `LoadGameContent`, колоды мест из `DeckRepository`, сид из
  `SeedGenerator`, раздача движком, стол с агентом бота против бота. Итог `sealed`: `MatchStarted(MatchSession)`,
  `MatchContentUnavailable`, `MatchDeckNotFound`, `MatchDeckInvalid`. Карты колоды идут в движок по UUID, чтобы сид
  однозначно задавал партию.
- `RecordFinishedMatch(session, finalView)`: запись в историю глазами `MatchSession.perspective` — первого здешнего
  места (в hot-seat первого игрока): итог, выигранные раунды, фракции, режим. Режим сессии — `MatchMode` истории
  партий (`hotSeat`, `ai`, позже `wifi` и другие), поэтому сетевая партия запишется тем же сценарием.
- `SeedGenerator` (core/domain) скрывает случайность сида; в приложении `SecureSeedGenerator` на `Random.secure`.

### Держатели состояния (presentation)

- `MatchSetupCubit`: режим (по умолчанию против бота) и колода каждого места; готовый выбор —
  `MatchSetupReady.request`. Удалённая колода снимается с выбора.
- `MatchBloc`: события `MatchStartRequested` (местная партия из колод), `MatchSessionOpened` (готовая партия, например
  сетевая из лобби: экран не знает, как она начата), `MatchIntentSubmitted`, `MatchHandoverAccepted` и внутреннее
  `MatchTableUpdated`; состояния `MatchIdle`, `MatchStarting`, `MatchStartFailed`, `MatchHandover`, `MatchInProgress`,
  `MatchFinished`, `MatchCrashed`. Сетевой режим добавит лобби со своим держателем, а партию передаст сюда через
  `MatchSessionOpened`; обработка стола в `MatchBloc` для него не меняется.
  - Держатель владеет столом: закрывает его при своём закрытии, в том числе если игрок ушёл с экрана, пока партия
    начиналась, и после `TableFailed`. Экран ошибки (`MatchCrashed`) окончательный: обновления стола его не заменяют.
    Неожиданное исключение при старте (например, хранилища) тоже даёт `MatchCrashed`, а не вечную загрузку.
  - Экран показывает партию глазами места, от которого партия ждёт действия (`awaitsAction`). В hot-seat при смене
    места, и в начале партии тоже, сначала идёт `MatchHandover(next)`: рука скрыта, пока следующий игрок не подтвердит.
  - События копятся отдельно для каждого места и отдаются, когда место снова на экране: игрок видит, что сделал
    соперник, пока телефон был у того.
  - Законченная партия сразу показывается (`MatchFinished`), затем записывается в историю (поле `record`). Ошибка
    записи не убирает итог с экрана и уходит в `addError`.
- Маршрут `/match` создаёт оба держателя; экран поля их пока не читает.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Держатель состояния сам вызывает движок и бота | Сетевой режим потребовал бы второго держателя: у гостя нет состояния партии, только проекции. |
| Сетевой игрок как агент местного стола | Повторяет `MatchHost` (журнал, пауза, переподключение, авторитетность), а гостю всё равно нужен стол поверх клиента. |
| Местная партия через `MatchHost` и `InMemoryTransport` | Одинаково для всех режимов, но hot-seat и бот платили бы за кодек, нумерацию и таймеры связи без пользы, а боту нужно полное состояние, которого у клиента нет. |
| Синхронный агент `Intent? decide(...)` | Нельзя ни сделать паузу «бот думает», ни вынести расчёт хода в изолят без смены контракта. |
| Отдельный поток обновлений на каждое место | Проекции мест приходили бы по очереди, и экран hot-seat видел бы рассинхрон между ними. |
