# 0003. Управление состоянием, внедрение зависимостей и каркас приложения

## Контекст

`CLAUDE.md` требует выбрать state management и DI до первого экрана. Ограничения, от которых зависит выбор:

- Чистая слоистая архитектура: domain → application → data / presentation, всё внешнее за интерфейсами, реализации подставляются в одной точке сборки, без глобальных синглтонов вне неё. В тестах фейки, а не моки.
- Состояния, действия и события описываются `sealed`-классами с исчерпывающим `switch`.
- Ядро игры — детерминированный движок `apply(state, seat, intent)`. Экран поля превращает действия игрока и сообщения сети в намерения и показывает проекцию состояния. Это поток событий с асинхронными источниками (сеть, таймеры, ИИ).
- Строгий линтер, кодогенерация только через `tools/scripts/setup.sh`, сгенерированный код не коммитится.
- Flutter закреплён на 3.41.0, поэтому пакеты, которым нужен `meta` 1.18 и выше (через свежий `analyzer`), не подходят.

## Решение

### Состояние экрана: `flutter_bloc`

- Держатель состояния экрана — `Cubit`. `Bloc` с `sealed`-событиями берём, когда важна последовательность событий (поле матча: намерения игрока, сообщения соперника, таймеры).
- Состояние — `sealed`-класс, виджет разбирает его исчерпывающим `switch` (пример: `DeckListState` и `DeckBuilderScreen`).
- Держатель получает сценарии (use cases) через конструктор и не знает о реализациях. Сценарии и движок не зависят от Flutter и `bloc`.
- Тесты держателей слушают `cubit.stream` обычными средствами `flutter_test`. Пакет `bloc_test` не подключён: его зависимость `test` несовместима с `drift_dev` при Flutter 3.41.0.

### Внедрение зависимостей: ручное, через точку сборки

- `lib/src/app/composition_root.dart` (`createAppDependencies`) — единственное место, где интерфейсы связываются с реализациями (Drift, системные часы, UUID). Её вызывает `lib/main.dart`.
- `AppDependencies` собирает сценарии над интерфейсами и ничего не знает о реализациях. Тесты создают его с фейками (`test/support/fakes.dart`).
- Навигация (`lib/src/app/router/app_router.dart`) создаёт держатели состояния на уровне маршрута (`BlocProvider(create: ...)`) и передаёт им сценарии из `AppDependencies`. Экраны берут держатель из дерева виджетов, а сервисы оттуда не достают.
- Ни сервис-локатора, ни DI-фреймворка, ни глобальных провайдеров.

### Навигация: `go_router` в слое `app`

- Пути в `AppRoutes`, вложенность маршрутов задаёт стек «назад».
- Экраны фич не знают о маршрутах и друг о друге: переходы приходят параметрами-колбэками (`MenuScreen(onDecks: ...)`).

### Хранилище: одна база Drift

- `AppDatabase` в `lib/src/core/database/`, таблицы в `tables/`. Репозитории фич (`features/*/data/`) реализуют доменные интерфейсы поверх неё.
- Колоды ссылаются на карты, лидеров и фракции только по UUID. Состав колоды лежит в отдельной таблице с каскадным удалением (`PRAGMA foreign_keys = ON` при открытии).
- Настройки хранятся парами «ключ — значение»: новая настройка не требует миграции, отсутствующий ключ даёт значение по умолчанию.
- Дата и время хранятся текстом ISO-8601 (`store_date_time_values_as_text`), без потери миллисекунд.
- Миграции: схема каждой версии коммитится в `drift_schemas/app_database/`. `setup.sh` запускает `drift_dev make-migrations`: он сохраняет схему новой версии, падает, если таблицы изменились без увеличения `schemaVersion`, и собирает шаги миграции `stepByStep`. Тестовые базы всех версий собирает `drift_dev schema generate`, а `test/drift/app_database/migration_test.dart` проверяет переход с каждой прежней версии и совпадение последней схемы с кодом.
- В CI `setup.sh` падает, если `make-migrations` создал файл схемы, которого нет в коммите: иначе схема новой версии терялась бы, а CI оставался зелёным.
- Значения enum (режим и итог партии) хранятся стабильными строковыми кодами, которые задаёт репозиторий, а не именами значений: переименование в домене не ломает данные, а общая база не зависит от доменов фич. Тест фиксирует коды.
- Моменты времени записываются в UTC: сортировка в SQL идёт по тексту ISO-8601 и верна только для одного пояса.
- `drift` и `drift_dev` закреплены точно на 2.34.0 и обновляются только вместе: `drift_dev` новее требует `analyzer` 13+ (а значит `meta` 1.18), а `drift` новее несовместим с `drift_dev` 2.34.0. При обновлении `drift_dev` проверить, не изменился ли формат JSON-схем: `make-migrations` сравнивает файл текущей версии целиком и упадёт на неизменённой схеме, если формат другой.

### Локализация: `gen-l10n`

- ARB в `lib/src/core/l10n/arb/`, шаблон `app_ru.arb`. Вывод в `lib/src/core/l10n/generated/` (не коммитится, создаёт `setup.sh`). Доступ: `context.l10n.<ключ>`.
- Единственная локаль `ru`; новый язык — новый ARB-файл.

### Проверка слоёв

`test/architecture_test.dart` разбирает импорты `lib/` и проверяет направление зависимостей: domain и application только чистый Dart, presentation без Drift, `dart:io` и UUID, data без presentation и application. Файл вне известного слоя роняет тест.

## Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Riverpod (с кодогенерацией или без) | Провайдеры объявляются глобально и смешивают DI с состоянием; граница «экран получает только сценарии» держится соглашением, а не конструктором. Кодогенерация добавляет ещё один `build_runner`-генератор с собственной версией `analyzer`, что при закреплённом Flutter сразу упирается в `meta`. Для потока событий матча `Bloc` с `sealed`-событиями даёт ту же выразительность проще. |
| `get_it` (+ `injectable`) | Сервис-локатор — глобальный синглтон, зависимости скрыты от конструктора; это прямо запрещено `CLAUDE.md`. |
| `provider` / `ChangeNotifier` | Изменяемое состояние без явных переходов; `sealed`-состояния и события пришлось бы строить вручную. |
| `signals`, MobX | Реактивность на изменяемых наблюдаемых полях, у MobX ещё и кодогенерация; расходится с неизменяемыми моделями и `sealed`-состояниями. |
| `setState` + `InheritedWidget` | Годится для заглушек, но для поля матча с сетью и таймерами превращается в самописный Bloc. |
| Навигатор 1.0 (`Navigator.push`) | Нет декларативных путей, которые понадобятся для восстановления лобби и диплинков на приглашение в сетевую игру. |
