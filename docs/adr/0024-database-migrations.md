# 0024. Миграции базы пользовательских данных

## Контекст

Колоды, настройки и история партий лежат в Drift (`AppDatabase`, ADR 0003). Приложение ставится поверх прежней сборки без удаления, поэтому после обновления база старой версии должна открыться и сохранить данные. Планы проекта (вне репозитория) предусматривают хранимые данные игрока, например коллекцию карт и прогресс: их потеря при обновлении недопустима.

Проверка (октябрь 2026): чтение кода `drift` 2.34.0 и пробные запуски на файлах базы во временной папке.

- Основа уже есть: схема каждой версии коммитится в `drift_schemas/app_database/`, `setup.sh` через `drift_dev make-migrations` падает при изменении таблиц (и настроек `build.yaml`, которые попадают в схему) без новой `schemaVersion` и собирает шаги `stepByStep`, `test/drift/app_database/migration_test.dart` идёт в CI. База v1 с колодой, картами и настройкой открывается текущим кодом (v2) без потерь.
- До этого ADR `onUpgrade` и `onCreate` не были обёрнуты в транзакцию. Я сымитировал сбой шага после создания таблицы: результат первой инструкции остался в базе при прежнем `user_version`. Повторный запуск того же шага безопасен не всегда: `createTable` пишет `CREATE TABLE IF NOT EXISTS` и пройдёт, а `addColumn` упадёт на «duplicate column name». Пока такой шаг не исправлен выходом новой сборки, приложение не открывается, а у игрока один выход: удалить данные. С обёрткой в транзакцию тот же сбой откатывался полностью.
- Базу новой версии нельзя открыть сборкой со старой схемой: Drift бросает общий `StateError` («Migration steps can only upgrade»). Данные целы. Пользователь решил, что откатов на старую сборку не будет, поэтому это не обрабатывается.
- Уже сохранённый файл схемы можно удалить или переписать и пересоздать: `setup.sh` и CI это пропускают (сообщение `drift_dev` само подсказывает такой выход).
- Тест миграции проверял форму таблиц (`migrateAndValidate`), но не сохранность данных.

## Решение

Правила для любого изменения схемы базы. Решения пользователя (20.10.2026): откатов на старую сборку не будет никогда, поэтому защита от открытия базы новой версии старой сборкой не делается; транзакция, проверка схем в CI и тест данных внедрены вместе с этим ADR.

### Версия и схема

1. Любое изменение, которое меняет файл базы, увеличивает `schemaVersion` ровно на 1 и дописывает шаг в `stepByStep`. Это таблицы, колонки, ограничения, индексы, триггеры и настройки `build.yaml`, меняющие хранение значений (например, `store_date_time_values_as_text`; они записаны в JSON схемы, и `make-migrations` сам падает при их смене без новой версии). Новая настройка (ключ в `Settings`) схемы не меняет (ADR 0003).
2. Файл схемы новой версии создаёт `setup.sh`, автор коммитит его в том же PR. Файл схемы версии, попавшей в `dev`, не редактируется, не удаляется и не пересоздаётся: ошибка исправляется следующей версией. Единственное исключение: при обновлении `drift_dev` меняется формат JSON (ADR 0003), и файлы схем переписываются отдельным PR без изменения самих таблиц. Пока версия не в `dev`, схему можно пересоздать (CLAUDE.md, «Команды»). Если два открытых PR подняли версию до одного номера, второй после слияния первого переносит свой шаг на следующий номер и пересоздаёт свой файл схемы.
3. Миграция идёт только вперёд. Версия не пропускается, `destructiveFallback` и удаление базы при ошибке запрещены. После попадания версии в `dev` её шаг не переписывается.

### Шаг миграции

4. Обновление с версии N до M выполняется целиком или откатывается целиком: `onUpgrade` оборачивается в транзакцию (`transaction(() => stepByStep(...)(m, from, to))`), `onCreate` тоже. Тогда сбой не оставляет базу на полпути, а повторять шаги идемпотентно не нужно. `PRAGMA foreign_keys = ON` остаётся в `beforeOpen`, то есть после миграции. Шаг с пересозданием таблицы (`TableMigration`) обязательно проверяется тестом данных с зависимыми таблицами (пункт 7). Реализация: `AppDatabase.migration`, шаги вынесены в `upgradeSteps`, тест сбоя подставляет туда падающий шаг.
5. Данные не теряются. Добавленная колонка получает значение по умолчанию или заполняется шагом; удаление и сужение типа допустимы только если данные переносятся в новую форму; переименование и смена типа делаются через `TableMigration`. Тип и смысл значений в колонках (UUID карт и фракций, моменты времени в UTC как текст, стабильные коды партий) не меняются без переноса данных.
6. UUID карты не меняется никогда (CLAUDE.md), поэтому колоды ссылаются на карту без миграции. Смена содержимого пакета контента — не миграция Drift: годность колоды проверяется при её выборе (ADR 0008), сохранённые колоды автоматически не переписываются.

### Тесты

7. Для каждого шага, добавленного после этого ADR, есть тест данных: база прежней версии создаётся из сгенерированной схемы (`test/drift/app_database/generated/`), в каждую таблицу базы кладутся строки, затем она мигрирует текущим `AppDatabase` (через `schema.rawDatabase` из `SchemaVerifier.schemaAt` или `SchemaVerifier.testWithDataIntegrity`), и проверяется, что строки на месте, а новые колонки и таблицы заполнены ожидаемо. `migrateAndValidate` одна недостаточна: она сверяет только форму таблиц. Тест лежит в `test/drift/app_database/`, идёт в CI и закрывает переходы со всех прежних версий. Для шага 1→2 тест данных уже есть.
8. Из шага миграции нельзя вызывать код приложения: репозитории, сценарии, модели домена. Шаг пользуется только таблицами схемы версии (`schema.<таблица>` из `stepByStep`) и SQL, иначе он ломается при изменении этого кода.

### Защита в CI и при запуске

9. CI на pull request сравнивает `drift_schemas/` с базовой веткой: допустимы только добавленные файлы, изменение и удаление существующих падает. Это `tools/scripts/check_schemas_immutable.sh` (шаг в `ci.yml`, ему нужна история: `fetch-depth: 0`); PR со сменой формата схем при обновлении `drift_dev` (исключение пункта 2) падает на нём осознанно, и решает пользователь.
10. База никогда не удаляется и не пересоздаётся автоматически. Сбой миграции оставляет данные в состоянии до обновления (пункт 4). Откат на сборку со старой схемой не поддерживается и не нужен: такая сборка не открывает базу новой версии (Drift бросает `StateError`).

### Порядок работы над изменением схемы

- **А.** Написать тест данных (пункт 7): он падает, пока шага нет.
- **Б.** Поправить таблицы, поднять `schemaVersion`.
- **В.** Запустить `tools/scripts/setup.sh`: появятся файл схемы и шаги `stepByStep`.
- **Г.** Дописать шаг в `AppDatabase.migration`, довести тест до зелёного.
- **Д.** Закоммитить файл схемы; в описании PR написать, какие данные затрагивает миграция.

## Отвергнутые варианты

- **Пересоздавать базу при несовпадении версий** (`destructiveFallback`): теряет колоды и прогресс.
- **Транзакция на каждый шаг отдельно**: сбой на шаге 4 при переходе 2→5 оставил бы базу на версии 3, и приложение всё равно не открылось бы. Транзакция на весь `onUpgrade` проще и надёжнее.
- **Копия файла базы перед миграцией**: самая прямая защита от потери, но добавляет работу с файлами в слой data, место на устройстве и свои сбои. Пересматривается, если миграции станут сложными.
- **Проверять схему только в тесте без файлов схем**: нечем воспроизвести базу прежней версии.
- **Свои SQL-файлы миграций и ручной `PRAGMA user_version`**: дублирует `drift_dev` и не проверяется тестами схем.

## Статус

Принято.
