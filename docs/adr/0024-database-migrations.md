# 0024. Миграции базы пользовательских данных

## Контекст

Колоды, настройки и история партий лежат в Drift (`AppDatabase`, ADR 0003). Приложение ставится поверх прежней сборки без удаления, поэтому после обновления база старой версии должна открыться и сохранить данные. В ближайших задачах в базу добавятся коллекция карт и прогресс игрока: потеря этих данных при обновлении недопустима.

Проверка на настоящих файлах базы (октябрь 2026) показала:

- Основа уже есть: схема каждой версии коммитится в `drift_schemas/app_database/`, `setup.sh` через `drift_dev make-migrations` падает при изменении таблиц без новой `schemaVersion` и собирает шаги `stepByStep`, `test/drift/app_database/migration_test.dart` идёт в CI. База v1 с колодой, картами и настройкой открывается текущим кодом (v2) без потерь.
- Шаги миграции не обёрнуты в транзакцию. Сбой после первой инструкции шага оставляет её результат в базе при прежнем номере версии, и следующий запуск падает на том же шаге («таблица уже существует»). Выход один: удалить приложение вместе с данными.
- Базу новой версии нельзя открыть сборкой со старой схемой: Drift бросает `StateError` («Migration steps can only upgrade»), обработчика нет. Данные при этом целы.
- Уже сохранённый файл схемы можно удалить или переписать и пересоздать: `setup.sh` и CI это пропускают (сообщение `drift_dev` само подсказывает такой выход).
- Тест миграции проверяет форму таблиц (`migrateAndValidate`), но не сохранность данных.

## Решение

Правила для любого изменения схемы базы. Пункты со знаком (*) требуют кода и вводятся отдельной задачей; пока её нет, они действуют как требования к ревью.

### Версия и схема

1. Любое изменение, которое меняет файл базы, увеличивает `schemaVersion` ровно на 1 и дописывает шаг в `stepByStep`. Это таблицы, колонки, ограничения, индексы, триггеры, а также настройки `build.yaml`, меняющие хранение значений (например, `store_date_time_values_as_text`). Новая настройка (ключ в `Settings`) схемы не меняет (ADR 0003).
2. Файл схемы новой версии создаёт `setup.sh` и коммитит автор в том же PR. Файл схемы версии, попавшей в `dev`, не редактируется, не удаляется и не пересоздаётся: ошибка исправляется следующей версией. Пока версия не в `dev`, схему можно пересоздать (CLAUDE.md, «Команды»).
3. Миграция идёт только вперёд. Версия не пропускается, шаг не переписывается, `destructiveFallback` и удаление базы при ошибке запрещены.

### Шаг миграции

4. (*) Каждый шаг выполняется целиком или не выполняется совсем: `onUpgrade` и `onCreate` оборачиваются в транзакцию (`transaction(() async { ... })`), чтобы сбой не оставлял базу на полпути. До внедрения шаг пишется так, чтобы его повторный запуск после сбоя был безопасен.
5. Данные не теряются. Добавленная колонка получает значение по умолчанию или заполняется шагом; удаление и сужение типа допустимы только если данные переносятся в новую форму; переименование делается через `TableMigration`. Тип и смысл значений в колонках (UUID карт и фракций, моменты времени в UTC как текст, стабильные коды партий) не меняются без переноса данных.
6. UUID карты не меняется никогда (CLAUDE.md), поэтому колоды и коллекция ссылаются на неё без миграции. Смена содержимого пакета контента — не миграция Drift: годность колод проверяет движок при чтении (ADR 0008), а переписывать сохранённые колоды автоматически мы не обязаны.

### Тесты

7. Для каждого шага есть тест, который создаёт базу прежней версии из сгенерированной схемы (`test/drift/app_database/generated/`), кладёт в неё строки каждой затронутой таблицы, мигрирует текущим `AppDatabase` и проверяет, что строки на месте, а новые колонки и таблицы заполнены ожидаемо. Одной `migrateAndValidate` недостаточно: она сверяет только форму таблиц. Тест миграции лежит в `test/drift/app_database/`, идёт в CI и закрывает переходы со всех прежних версий.
8. Из шага миграции нельзя вызывать код приложения: репозитории, сценарии, модели домена. Шаг пользуется только таблицами схемы версии (`schema.<таблица>` из `stepByStep`) и SQL, иначе он ломается при изменении этого кода.

### Защита в CI и при запуске

9. (*) CI на pull request сравнивает `drift_schemas/` с базовой веткой: допустимы только добавленные файлы, изменение и удаление существующих падает.
10. (*) Открытие базы новой версии сборкой со старой схемой не должно ронять приложение молча: пользователь видит понятное сообщение «Обновите приложение», данные не удаляются и не перезаписываются.
11. База никогда не удаляется и не пересоздаётся автоматически. Сбой миграции доводится до пользователя как ошибка, данные остаются как были (после пункта 4 — в состоянии до шага).

### Порядок работы над изменением схемы

1. Поправить таблицы, поднять `schemaVersion`.
2. Запустить `tools/scripts/setup.sh`: появятся файл схемы и шаги `stepByStep`.
3. Дописать шаг в `AppDatabase.migration`.
4. Написать тест данных (пункт 7).
5. Закоммитить файл схемы; в описании PR написать, какие данные затрагивает миграция.

## Отвергнутые варианты

- **Пересоздавать базу при несовпадении версий** (`destructiveFallback`): теряет колоды и будущий прогресс.
- **Проверять схему только в тесте без файлов схем**: нечем воспроизвести базу прежней версии.
- **`PRAGMA user_version` вручную и свои SQL-файлы миграций**: дублирует то, что даёт `drift_dev`, и не проверяется тестами схем.

## Статус

Предложено. Пункты 1–3, 5–8 и 11 действуют сразу (на них опираются CLAUDE.md и ревью). Пункты 4, 9 и 10 ждут решения пользователя и отдельной задачи.
